## 2. 项目概述

### 2.1 项目背景

政策文件数量大、层级多、更新频繁。传统关键词搜索难以同时处理自然语言意图、适用地区、适用对象、政策状态和效力层级。工作人员在政策查询、公文起草、咨询答复和政策研究中，需要反复查找原文、核对条款并确认时效，工作成本高且容易遗漏。

policy-knowledge-base 拟建设一套专业政策知识库与智能政策分析平台，以可持续维护的政策数据为事实基础，以条款级检索和来源追溯为核心，通过 AI 辅助理解、摘要与表达，但不使用模型生成内容替代政策原文、权威解释或专业人员的最终判断。

### 2.2 项目定位

- 产品定位：专业政策知识库与智能政策分析平台。
- 核心理念：让政策更容易找到、理解、比较和使用。
- 首期主场景：可追溯政策问答。
- 核心价值：每个政策性结论均可回到文件、条款和原文进行核验。
- 首期差异化能力：**政策文件的准实时采集**（新政策分钟级进入知识库）与**条款级可追溯问答**。
- 首期辅助能力：政策解读、信息摘要与知识关联，帮助用户理解和比较政策。

### 2.3 建设原则

1. **事实可信**：政策数据库及原始政策文件是事实来源。
2. **证据优先**：政策性结论必须关联来源和条款位置。
3. **状态明确**：区分现行有效、尚未生效、已修订、部分失效、已废止和历史版本。
4. **AI 克制**：AI 负责意图理解和信息表达，不代替权威解释与人工审查。
5. **范围受控**：先完成可信 MVP 闭环，再扩大政策范围和分析能力。
6. **分阶段验收**：每一阶段均设置明确交付物和退出条件。
7. **时效可控**：采集频率与范围受配置约束，不因追求实时性突破合规边界或来源站点承载能力。

## 3. 项目目标与成功标准

### 3.1 首期目标

首期不追求一次性建设完整政策平台，而是验证以下可信闭环：

```text
政策文件准实时采集 / 管理员导入
  → 文本解析与条款拆分
  → 元数据校验和审核入库
  → 关键词与向量混合检索
  → 候选重排和证据组装
  → 基于证据生成回答
  → 来源核验、日志留痕和用户反馈
```

系统应能够在一组边界清晰、来源明确的真实政策文件中，完成稳定入库、条款级检索和可追溯回答。当条件不完整或证据不足时，系统应主动澄清或拒答。

### 3.2 成功标准

- 指定样本文件能够稳定、可重复地导入和解析；
- 配置站点新发布的政策能够在约定时延内自动进入可检索状态；
- 政策知识块能够反向定位到政策版本、原文件和条款上下文；
- 用户能够通过关键词、自然语言和元数据条件检索政策；
- 回答包含文件名称、条款位置、原文片段和政策状态；
- 政策解读、摘要和关联结论同样可回到条款原文核验；
- 不存在可靠证据时，系统不补写政策内容；
- 需求、实现、测试及验收证据可相互追溯；
- 核心评测指标在冻结数据集和约定环境下达到正式确认的门槛。

## 4. 用户与核心场景

### 4.1 用户角色

| 用户角色 | 主要任务 | 首期优先级 |
|---|---|---|
| 政策查询使用者 | 查找适用政策和具体条款 | P0 |
| 公文撰写人员 | 获取可核验的政策依据 | P0 |
| 公众咨询受理人员 | 按地区、对象和时间定位条款 | P0 |
| 知识库管理员 | 导入、校验、修正和停用政策数据，配置采集源 | P0 |
| 政策研究人员 | 浏览、筛选、比较政策，查看解读、摘要与关联关系 | P0 |
| 政策制定或审查人员 | 发现潜在冲突、重复和层级问题 | PoC |

### 4.2 查询与问答流程

1. 用户输入自然语言问题或搜索内容。
2. 系统识别主题、地区、对象、时间和行为等约束。
3. 关键条件缺失或存在歧义时，系统先提出澄清问题。
4. 系统执行元数据过滤、全文检索和语义检索。
5. 系统给出简明结论及对应证据。
6. 用户可展开查看文件、条款、原文、状态及完整上下文。
7. 用户可补充约束继续查询，或提交结果反馈。

### 4.3 政策入库流程

1. 管理员上传文件并填写或确认基础信息。
2. 系统解析正文、识别结构、生成知识块和标签。
3. 管理员检查低置信字段、异常结构和解析失败项。
4. 审核通过的数据进入可检索状态。
5. 修正和重新处理须保留版本与操作记录。

### 4.4 冲突初筛流程

1. 用户提交拟定条款并选择比对范围。
2. 系统拆分条款并召回相关现行政策。
3. 系统输出潜在冲突、疑似重复、潜在层级违背或无明显冲突。
4. 每项结果展示双方原文、来源、判断理由和置信信息。
5. 业务人员对机器建议进行确认或驳回。

该能力仅作为受控 PoC，结果属于风险线索，不构成法律结论。

### 4.5 实时采集流程

1. 管理员配置采集源（站点、栏目、等级、频率、主题与地区标签）。
2. 采集器按分级周期轮询或接收订阅事件，识别新增与变更文件。
3. 下载原文与附件，指纹去重后进入导入流程（4.3）。
4. 系统自动完成解析、条款拆分、打标与向量化，达到可检索状态。
5. 变更类型（新增、修订、废止、更正）同步更新政策状态与版本关系。
6. 新政策进入“最新政策”动态流，并按订阅条件推送给相关用户。
7. 采集异常进入失败列表，支持重试、人工补录和告警。

采集范围以配置清单为准，只采集公开政策栏目，不追求覆盖全国、全层级、全历史政策。

### 4.6 政策解读与知识关联流程

1. 用户打开政策详情或指定条款，选择解读、摘要或关联视图。
2. 系统基于该政策原文与知识块生成结构化解读或多级摘要。
3. 系统展示上位法、下位配套、同位阶相关文件及引用关系。
4. 每个结论与关联项均附条款来源，支持点击跳转核验。
5. 用户可反馈结论是否有用或错误，用于后续优化。

冲突初筛流程见 4.4，仍为受控 PoC。

## 5. 项目范围

### 5.1 MVP 必须交付

- 受控导入 PDF、DOCX、TXT、HTML 政策文件；
- **按配置清单准实时采集公开政策栏目，新政策分钟级进入可检索状态**；
- 保存原文件、内容哈希、来源网址、导入信息和解析器版本；
- 抽取文件级元数据，并拆分到“条”，单条超长（超过 500 字）或含多款独立事项时拆分到“款”；
- 管理主题、地区、发文机关、效力层级和时效状态等标签（取值字典见 10.4、10.5）；
- 支持关键词检索、语义检索、元数据过滤和结果重排；
- 支持政策详情、条款上下文和稳定来源定位；
- 支持带文件名、条款位置、原文片段和状态的可追溯问答；
- 支持条件澄清、证据不足拒答和会话约束继承；
- **支持政策解读、信息摘要与知识关联（上位法、同位阶、引用关系）**；
- **支持“最新政策”动态流与变更提示（新增、修订、废止）**；
- **支持政策修订、废止、替代关系及版本对比**；
- 提供文件、任务、采集源、解析结果、人工校验和停用等基础管理能力；
- 记录导入、检索、模型调用、证据和关键管理操作日志，并支持导出；
- 建立版本化评测集并输出可重复执行的评测报告。

### 5.2 验证性范围

在限定政策主题、效力层级和冻结样本集内，验证以下能力：

- 潜在条款冲突；
- 疑似重复；
- 潜在层级违背。

结果必须明确标注为“机器辅助初筛”，并支持人工确认或驳回。

### 5.3 不在 MVP 范围

- 覆盖全国、全层级、全历史政策；采集仅按配置清单在指定站点与栏目内进行；
- 突破来源站点访问控制、绕过验证码或使用代理池规避限流；
- 全自动判定政策生命周期及法律效力；
- 无人工复核的法律合规结论；
- 面向公众直接发布的权威政策解释；
- 面向所有行业的申报匹配和复杂政策推荐；
- 自动生成可直接发布的公文或法律意见；
- 复杂组织权限、计费、CRM 和客户服务体系；
- 未经验证的客户案例、效率提升、成功率或商业承诺；
- 未明确环境和资源前承诺高并发、99% 可用性等生产指标；
- 扫描件 OCR（视首批文件扫描件占比决定，见 DEC-011）。

### 5.4 后续版本候选

- **V1.1 范围扩展**：扩大采集站点与政策主题、跨地区政策对比、政策提醒订阅推送（邮件与企业微信通道）。
- **V1.2 分析扩展**：政策图谱可视化、政策匹配、结构化报告导出、政策变化影响分析。
- **V2.0 生产化**：组织权限体系、外部系统集成、规模化部署、监控告警、备份恢复和安全测评。

## 6. 产品需求

### 6.1 产品规则

- 每个政策性结论必须映射到至少一个证据块；
- 证据至少包含文件名、条款位置、原文片段和时效状态；
- 无可靠证据时返回“未找到足够政策依据”，并提示用户补充条件；
- 已废止或不在当前适用范围的政策不得默认作为现行依据；
- 政策原文与 AI 生成解释必须在视觉和数据结构上明确区分；
- 冲突分析必须声明辅助初筛性质，并要求人工复核；
- 正式名称使用“policy-knowledge-base”或“政策知识库”；
- 不使用未经批准的品牌名、统计数字和商业承诺。

## 9. 总体技术方案

### 9.1 技术设计目标

- 来源可追溯优先于回答流畅度；
- 首期以最少基础设施完成端到端闭环；
- 文档解析、检索、模型和存储通过接口隔离；
- 异步任务可重试、可观察、可审计；
- 首期每类能力只保留一个主方案，避免多套技术并行建设。

### 9.2 逻辑架构

```text
Vue3 工作台 / 管理后台
            │
FastAPI 接口层 / 认证与鉴权
            │
应用服务
  ├─ 采集编排（调度、去重、变更识别）
  ├─ 政策管理与导入编排
  ├─ 检索与问答编排
  ├─ 解读、摘要与知识关联
  ├─ 会话与反馈
  └─ 冲突初筛 PoC
            │
领域与基础设施适配
  ├─ 文档解析器（PyMuPDF / python-docx / Unstructured）
  ├─ PostgreSQL（元数据、知识块、任务、日志）
  ├─ Milvus / FAISS（向量检索）
  ├─ MinIO 对象存储（原文件）
  ├─ Model Gateway（DeepSeek API + BGE-M3 + Reranker）
  └─ Celery + Redis（异步任务、队列与削峰）
```

### 9.3 首期技术选择

| 能力 | 主方案 | 说明 |
|---|---|---|
| 服务端 | Python 3.11 + FastAPI | 生态成熟，便于集成解析、向量检索与模型调用 |
| 前端 | Vue 3 + Element Plus | 桌面端优先，组件齐全，交付周期短 |
| 关系数据 | PostgreSQL | 保存政策、知识块、状态、会话和日志索引 |
| 向量检索 | Milvus（主）/ FAISS（单机与演示） | 知识块规模增长后可平滑切换 |
| 全文检索 | PostgreSQL 全文检索 + 中文分词扩展 | 条款号、发文字号等精确召回，与向量检索融合 |
| 文件存储 | MinIO（兼容 S3） | 保存原文件和派生文件 |
| 异步任务 | Celery + Redis | 执行采集、解析、向量化和索引构建 |
| 采集 | Scrapy + Scrapy-Redis，动态页用 Playwright | 分布式采集，配置化接入新站点 |
| 采集调度 | Celery Beat + APScheduler | 分级轮询与 RSS/Atom 订阅适配 |
| 增量识别 | SimHash 指纹 + BloomFilter + ETag/Last-Modified | 避免全量重爬 |
| 生成模型 | DeepSeek API（deepseek-chat / deepseek-reasoner） | 通过 Model Gateway 封装，可切换合规通道 |
| Embedding | BGE-M3（本地部署，1024 维） | **DeepSeek 不提供 Embedding 接口，必须使用独立模型** |
| 重排序 | BGE-Reranker-v2-m3（本地部署） | 对 Top20 候选重排取 Top5 |
| 缓存 | Redis | 会话、检索结果缓存与队列削峰 |

### 9.4 数据处理流程

1. 保存原始文件（采集或上传）并计算内容哈希，创建导入任务。
2. 解析文本、页码和结构信息，保存带版本的中间结果。
3. 抽取元数据，执行格式、日期、字典和人工确认校验。
4. 按政策结构生成知识块，保留前后文与稳定来源定位。
5. 生成检索文本、关键词和向量并更新索引。
6. 审核通过后，将对应政策版本切换为可检索状态。

### 9.5 检索与问答流程

1. 解析问题约束，判断是否需要澄清。
2. 执行元数据过滤、全文召回和向量召回。
3. 合并、去重并重排候选证据。
4. 应用最低相关性、适用范围和时效规则。
5. 组装带知识块 ID 的证据上下文。
6. 要求模型输出结构化回答及证据映射。
7. 服务端校验引用有效性，失败时重试或拒答。
8. 保存完整检索链路、最终证据和响应指标。

### 9.7 关键技术验证

- 中文全文检索对条款号、发文字号和政策术语的召回效果；
- PDF 页码和正文定位在不同文件类型中的稳定性；
- 获批 Embedding 和重排模型对中文政策语义的效果（BGE-M3 在政策语料上的基线）；
- 模型结构化输出与引用校验的失败率；
- 首批数据中扫描件的占比及 OCR 纳入 MVP 的必要性；
- **目标站点列表页结构稳定性与增量识别准确率**；
- **端到端采集时延能否在既定轮询周期内达成**（含解析与向量化耗时）。

### 9.8 实时采集方案

#### 9.8.1 触发机制

| 通道 | 适用场景 | 时延 |
|---|---|---|
| RSS/Atom 订阅 | 提供订阅接口的站点 | 秒级至分钟级 |
| 分级定时轮询 | 无订阅接口的站点：核心 5 分钟、一般 30 分钟、长尾每日 | 分钟级至小时级 |
| 手动触发 | 补爬、历史补录、重点专题 | 按需 |

#### 9.8.2 增量识别

1. 比对 `Last-Modified` / `ETag`，未变更则跳过详情页抓取；
2. 仅比对列表页前 50 条标题与链接，命中已采指纹即停止遍历；
3. 正文计算 SimHash，结合 BloomFilter 判重；
4. 以“标题 + 发文字号”作为业务主键兜底。

#### 9.8.3 实时入库流水线

```text
发现新/变更文件 → 下载原文 → 指纹去重 → 入队
  → 解析 → 条款拆分 → 元数据与标签 → 上位法与关联关系
  → Embedding 向量化 → 索引刷新 → 可检索
  → 变更事件广播（动态流 / 订阅推送）
```

- 全链路异步流水线，不同文件分阶段并行；
- **先入库、后复核**：自动抽取结果标记“待确认”但可被检索，人工复核修正后自动刷新索引；
- 索引写入后立即刷新，避免“已入库但搜不到”。

#### 9.8.4 变更联动

- **新增**：完整入库并进入动态流；
- **修订**：生成新版本，保留旧版本，建立 `revised_from` 关系；
- **废止**：不删除原文，状态置为“已废止”，检索降权但可查，用于历史依据核查；
- **部分失效**：按条款粒度标记，未失效条款保持现行有效。

#### 9.8.5 合规与降级

- 遵守 robots 协议，单站点默认 QPS ≤ 1，错峰调度，明确 User-Agent；
- 不使用代理池绕过访问控制、不破解验证码；遇强反爬改为人工补录或申请数据接口；
- 失败指数退避重试 3 次；连续失败 24 小时的站点降级为长尾频次并告警；
- 列表页连续 3 轮抽取为空判定为站点改版，自动冻结该源并通知管理员。

#### 9.8.6 可观测性

监控端到端时延 P95、单站点成功率、队列积压量、解析失败率、站点改版检测，任一超阈值触发告警并在管理后台可见。

### 10.5 效力位阶表与判定规则

**位阶表（依据《立法法》）**

| 位阶序号 | 规范类型 | 制定机关 |
|---|---|---|
| 1 | 宪法 | 全国人民代表大会 |
| 2 | 法律 | 全国人大及其常务委员会 |
| 3 | 行政法规 | 国务院 |
| 4 | 地方性法规（省级） | 省、自治区、直辖市人大及其常委会 |
| 5 | 地方性法规（设区的市） | 设区的市人大及其常委会 |
| 6 | 部门规章 | 国务院各部、委员会等 |
| 6 | 地方政府规章 | 省级、设区的市级人民政府 |
| 7 | 规范性文件 | 各级行政机关 |

**判定规则**

1. 位阶序号越小效力越高，下位法不得与上位法相抵触。
2. 地方性法规的效力高于本级和下级地方政府规章。
3. 部门规章与地方政府规章同等效力，在各自权限范围内施行。
4. **地方性法规与部门规章不构成上下位关系**：不一致时由国务院提出意见或提请全国人大常委会裁决；系统对此不作“层级违背”判定，输出“效力冲突待裁决”提示并列出双方条款。
5. 规范性文件位阶最低，不得设定行政许可、行政处罚、行政强制。
6. 冲突初筛中“潜在层级违背”的判定必须基于本表，由代码硬约束，不由模型自由判断。

## 12. 验收与评测方案

1. 文档与范围验收：需求、设计、决策和交付物完整一致。

5. 问答评测：答案、引用、拒答和约束遵循达到要求。
6. 非功能验收：性能、安全、审计和可维护性符合约定。

### 12.2 评测集要求

- 区分开发集与冻结验收集，验收集不得用于提示词或阈值调优；

- 由政策业务专家标注，争议样本须由第二人复核并记录裁决；本次由阮晴组织标注，全员参与复核；

| 评测口径不完整 | 无法客观验收 | 先冻结评测集和标注规则，再确认指标 |
| 冲突检测被当作法律结论 | 带来合规和声誉风险 | 限定 PoC 范围、显著提示、强制人工复核 |
| 技术方案过多 | 首期集成成本和进度风险增加 | 每类能力保留一个主方案和一个备选方案 |
| 数据向未批准模型通道出域 | 产生安全和合规风险 | 建立模型网关、通道白名单和审计日志 |
| 原型包含虚构数据或承诺 | 对外形成错误认知 | 标为演示内容，发布前由业务和法务审核 |
| 采集站点改版或限流 | 数据缺失、时延超标、合规风险 | 结构变化检测并冻结异常源、分级频率与 QPS 上限、人工补录通道 |
| 实时入库缺少人工审核 | 错误标签短暂可见 | 先入库后复核，结果标注“待确认”，复核修正后自动刷新索引 |
| 集中出台时段流量峰值 | 入库积压、时延超标 | 队列削峰、采集器水平扩展、积压告警 |
| 向量库与 Embedding 选型不当 | 检索准确率不达阈值 | 首期固定 BGE-M3 基线，在真实语料上验证后再调整 |
| 工期不足 2 天 | 功能无法全部完成，质量下降 | 按 11.3 优先级裁剪，保底最小闭环；未完成项列入遗留说明，不虚构完成度 |
| 评测集来不及标注 | 无法提供正式指标 | 先做 30～50 条小规模基线，如实标注样本量与未覆盖范围 |
| 团队 4 人并行开发冲突 | 返工与集成失败 | 按模块切分并固定接口（采集/解析、检索问答、前端），当日多次合并 |

## 17. 当前决策记录

### ADR-000 文档结构初始化

- 日期：2026-09-16
- 状态：已采用
- 结论：项目材料按项目管理、产品需求、技术设计、验收评测、会议决策和参考资料分区维护；本项目书作为 GitLab 单文件评审入口。
- 理由：既保留各主题独立维护能力，又提供一份可独立阅读的完整项目基线。

### ADR-001 首期范围建议

- 日期：2026-09-16
- 状态：待项目负责人批准
- 结论：MVP 优先完成政策入库、条款级混合检索和可追溯问答；冲突检测仅作为受控 PoC。
- 理由：优先验证事实和证据闭环，降低多项高风险能力同步建设导致的延期和不可验收风险。

### ADR-002 技术栈选型

- 日期：2026-09-22
- 状态：已采用
- 结论：服务端 Python 3.11 + FastAPI；向量检索 Milvus（主）/ FAISS（单机与演示）；前端 Vue 3 + Element Plus；异步任务 Celery + Redis；对象存储 MinIO。
- 理由：RAG 相关生态（解析、向量库、Embedding、重排）以 Python 为主，集成成本最低；Vue 3 组件齐全、上手快，适合 4 人小团队在有限周期内交付。

### ADR-003 实时采集纳入 MVP

- 日期：2026-09-22
- 状态：已采用
- 结论：按配置清单对指定政府公开栏目做准实时采集（核心站点 5 分钟、一般站点 30 分钟、长尾每日），新政策分钟级进入可检索状态；不追求覆盖全国全层级全历史。
- 理由：政策时效性是本项目区别于静态知识库的核心价值；通过配置清单与频率分级控制范围与合规风险。

### ADR-004 效力位阶由规则表硬约束

- 日期：2026-09-22
- 状态：已采用
- 结论：效力层级取值与位阶序号取自字典与位阶表（10.4、10.5），层级违背判定由代码实现；地方性法规与部门规章不作上下位判定，输出“效力冲突待裁决”。
- 理由：法律效力判定不能交由模型自由生成，否则存在实质性错误与合规风险。

### ADR-005 解读关联纳入 MVP、冲突检测维持 PoC

- 日期：2026-09-22
- 状态：已采用
- 结论：政策解读、信息摘要与知识关联纳入 MVP；冲突初筛维持受控 PoC，结果标注为机器辅助线索并强制人工复核。
- 理由：解读与摘要可复用已有证据链，风险可控；冲突检测的法律判定风险高，仍应由人工确认后使用。

### ADR-006 团队分工与交付物责任人

- 日期：2026-09-22
- 状态：已采用
- 结论：曹智成（负责与产品、作品材料）、姚子函（技术与后端 AI）、杨健（前端）、阮晴（测试评测与业务验收），赛事交付物 D-01～D-08 各有唯一责任人（见 11.2）。
- 理由：4 人团队需避免职责交叉导致交付遗漏，每项交付物明确到人。

### ADR-007 交付截止日期与裁剪策略

- 日期：2026-09-22
- 状态：已采用
- 结论：交付截止日期为 2026-09-23；保底交付项目书定稿、作品材料与“导入/采集 → 检索 → 可追溯问答”最小闭环；时间不足时按 11.3 的优先级从后往前裁剪，未完成项列入遗留说明。
- 理由：可用工期不足 2 天，与其全量铺开导致每个环节都不可用，不如保证核心闭环真实可演示；对外材料不得出现未实现的指标或功能承诺。
